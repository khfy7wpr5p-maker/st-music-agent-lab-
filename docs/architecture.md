# ST Music Agent Lab — Architecture Map

Status: A1-A13 guarded agent + four-project music evidence foundation
Date: 2026-09-11

## Purpose

ST Music Agent Lab is a model-agnostic engineering and music-intelligence agent layer. It
coordinates models and tools around ST repositories while keeping autonomy observable,
reversible, capability-driven and isolated from the host.

## Core design

The ST core stays small and framework-independent. Models, OpenHands, GitHub and music projects
attach through explicit adapters. No external framework may bypass ST-owned policy, tool,
budget, approval, evidence or sandbox boundaries.

## A1-A3 — Contracts, routing and policy

- `contracts.py`: tasks, model capabilities and action-risk contracts.
- `catalog.py` / `router.py`: capability-driven model selection.
- `policy.py` / `tools.py`: deterministic privilege gates independent from the LLM.

Initial profiles use GLM-5.1 for primary agentic engineering, Qwen3.8 as a secondary long-context
profile and Kimi-K2.5 for multimodal/score-image work.

## A4-A6 — Execution and isolation

- A4: OpenAI-compatible provider, CLI, credential/HTTP boundaries and OpenHands REST adapter.
- A5: repository-confined workspace and narrow command classifier.
- A6: disposable Docker sandbox with digest-pinned image, no network, dropped capabilities,
  `no-new-privileges`, resource limits and scoped repository mounts.

## A7-A8 — Structured tools and provider loop

- `agent_tools.py`: explicit allowlisted registry; unknown tools do not execute.
- `output.py`: bounded/redacted model-facing output.
- `journal.py`: sanitized append-only evidence with SHA-256 hash chain.
- `tool_loop.py`: canonical provider function calls with protocol and run budgets.
- `github_read.py`: bounded read-only GitHub metadata/file/branch/PR/workflow access.

Provider reasoning state may be replayed only inside provider history; it is not emitted as public
output or durable run evidence.

## A9-A10 — Controlled mutation and human approval

A9 exposes only reversible GitHub feature-branch creation/file writes to the model. Protected
branches, deletion and external side effects remain gated; merge is not a model tool.

A10 adds cumulative run time/turn/tool/byte budgets and opaque one-shot host approval tickets.
Approvals bind one exact action + target and cannot be generated by model arguments.

## A11 — Restricted OpenHands bridge

OpenHands Agent Server can attach to the ST registry through one MCP bridge without receiving raw
terminal/editor authority.

Bridged configuration:

- `agent.tools = []`;
- safe OpenHands defaults: `FinishTool`, `ThinkTool` only;
- one `st_tools` Streamable-HTTP MCP server;
- exact anchored filter derived from the concrete ST ToolRegistry manifest;
- remote bridge requires HTTPS; optional bearer credential resolves at the trusted host boundary.

`STToolBridge` projects only registry definitions, bounds names/arguments/time/tool calls and
dispatches every invocation back through the same ST registry. Unknown tools cannot be dynamically
resolved/imported.

## A12-A13 — Music-domain evidence plane

Music integration is read-only and evidence-first. `MusicEvidenceSnapshot` schema `1.1.0`
contains project, authority, state, bounded claims/warnings, optional next-safe-boundary and
source provenance (`repository`, `ref`, `path`, Git blob SHA).

Adapters fail closed when authoritative evidence is truncated, malformed or drifts away from
required safety/contract markers.

## Composition

`build_default_music_domain_toolset()` creates read-only clients for all four repositories and
returns `FullMusicDomainToolset`. The same registry flows through either provider route:

```text
Direct provider
      |
      v
 ToolRegistry -------------------------+
      |                                |
      |                         music.* snapshots
      |                         /   /   /   \
      |                        v   v   v     v
      |                    Restore TAB Editor Following
      |                        read-only GitHub evidence
      |
      +-> guarded generic tools / policy-aware feature-branch mutations

OpenHands Agent Server
      |
      | exact ST MCP allowlist
      v
 STToolBridge -> same ToolRegistry
```

There is no separate music privilege channel.

## Architectural invariants

1. Model choice is replaceable.
2. Models cannot grant themselves privileges or approvals.
3. Unknown/unregistered tools never execute.
4. Protected/destructive/external actions cannot silently escalate.
5. Credentials resolve only at trusted adapter boundaries after policy permits execution.
6. File operations cannot escape configured repository/workspace boundaries.
7. Host process execution is not a raw model capability.
8. Executable repository code runs only through an ST-approved sandbox backend.
9. Model-facing output/run traffic is bounded and redacted.
10. Persistent run evidence is sanitized and hash chained.
11. Provider schemas are not host authorization.
12. GitHub model mutation remains limited to reversible feature-branch operations.
13. Run budgets fail closed before overflowing the next action.
14. Approval artifacts are host-generated, exact-match and one-shot.
15. OpenHands raw terminal/editor tools are absent from the bridged agent configuration.
16. OpenHands discovers only the concrete ST registry manifest plus safe finish/think tools.
17. External frameworks cannot bypass ST policy, budget or isolation.
18. Music evidence is source-provenanced and cannot silently overstate readiness/authority.
19. Score Restore evaluation success never implies production or Stage 12 authorization.
20. REVIEW_REQUIRED never implies canonical TAB export.
21. Score Editor feature completion never implies release or SesliTab cutover authorization.
22. Score-following research evidence never implies acoustic-mixture, production or pedagogical
    authority.
23. Music-specific intelligence stays above generic execution infrastructure.
24. Tests define safety behavior before capability is widened.
