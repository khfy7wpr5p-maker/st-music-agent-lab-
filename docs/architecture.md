# ST Music Agent Lab — Architecture Map

Status: A1-A15 guarded agent + verified planning/learning foundation
Date: 2026-09-11

## Purpose

ST Music Agent Lab is a model-agnostic engineering and music-intelligence agent layer. It
coordinates models and tools around ST repositories while keeping autonomy observable,
reversible, capability-driven and isolated from the host.

## Core design

The ST core stays small and framework-independent. Models, OpenHands, GitHub and music projects
attach through explicit adapters. No external framework may bypass ST-owned policy, tool,
budget, approval, evidence, verification, learning or sandbox boundaries.

## A1-A3 — Contracts, routing and policy

- `contracts.py`: tasks, model capabilities and action-risk contracts.
- `catalog.py` / `router.py`: capability-driven model selection.
- `policy.py` / `tools.py`: deterministic privilege gates independent from the LLM.

Initial profiles use GLM-5.1 for primary agentic engineering, Qwen3.8 as a secondary long-context
profile and Kimi-K2.5 for multimodal/score-image work.

## A4-A6 — Execution and isolation

- A4: OpenAI-compatible provider, CLI, credential/HTTP boundaries and OpenHands REST adapter.
- A5: repository-confined workspace and narrow command classifier.
- A6: disposable Docker sandbox with digest-pinned image, no network, dropped capabilities,
  `no-new-privileges`, resource limits and scoped repository mounts.

## A7-A8 — Structured tools and provider loop

- `agent_tools.py`: explicit allowlisted registry; unknown tools do not execute.
- `output.py`: bounded/redacted model-facing output.
- `journal.py`: sanitized append-only evidence with SHA-256 hash chain.
- `tool_loop.py`: canonical provider function calls with protocol and run budgets.
- `github_read.py`: bounded read-only GitHub metadata/file/branch/PR/workflow access.

Provider reasoning state may be replayed only inside provider history; it is not emitted as public
output or durable run evidence.

## A9-A10 — Controlled mutation and human approval

A9 exposes only reversible GitHub feature-branch creation/file writes to the model. Protected
branches, deletion and external side effects remain gated; merge is not a model tool.

A10 adds cumulative run time/turn/tool/byte budgets and opaque one-shot host approval tickets.
Approvals bind one exact action + target and cannot be generated by model arguments.

## A11 — Restricted OpenHands bridge

OpenHands Agent Server can attach to the ST registry through one MCP bridge without receiving raw
terminal/editor authority.

- `agent.tools = []`;
- safe OpenHands defaults: `FinishTool`, `ThinkTool` only;
- one `st_tools` Streamable-HTTP MCP server;
- exact anchored filter derived from the concrete ST ToolRegistry manifest;
- remote bridge requires HTTPS; optional bearer credential resolves at the trusted host boundary.

`STToolBridge` projects only registry definitions, bounds names/arguments/time/tool calls and
dispatches every invocation back through the same ST registry. Unknown tools cannot be dynamically
resolved/imported.

## A12-A13 — Four-project music evidence plane

`MusicEvidenceSnapshot` schema `1.1.0` contains project, authority, state, bounded claims/warnings,
optional next-safe-boundary and source provenance (`repository`, `ref`, `path`, Git blob SHA).
Adapters fail closed when authoritative evidence is truncated, malformed or drifts away from
required safety/contract markers.

### Score Restore

Tool: `music.score_restore.snapshot`

Evaluation/candidate success never implies final model selection, Stage 12 entry, production
inference, OMR correctness or musical truth.

### MusicXML -> Guitar TAB

Tool: `music.tab_engine.capability_snapshot`

REVIEW_REQUIRED is capability-driven. Provisional TAB/playback may remain usable, while canonical
TAB/export remain PASS-only and BLOCKED remains safety-disabling.

### Score Editor

Tool: `music.score_editor.snapshot`

APP-11F completion does not open the standalone release matrix or authorize SesliTab V4 cutover.
APP-11G is the current declared next feature boundary.

### Real-Time Score Following

Tool: `music.score_following.snapshot`

SF-11 channel-separated research evidence is not acoustic-mixture, production or pedagogical
authority. SF-12 remains the next research stage.

## A14 — Deterministic cross-project planner

`portfolio_planning.py` adds a planning layer above the four repository-owned snapshots.

`CrossProjectPlanner` requires exactly the complete four-project evidence set at the supported
schema. Every source must retain repository/ref/path/blob-SHA provenance and every project must
declare a non-empty next safe boundary.

The current policy version is `2026-09-11.v1`. It deliberately closes bounded
validation/integration uncertainty before capability expansion or new research:

1. Score Restore — frozen-candidate non-training consumer/inference integration checks;
2. MusicXML/TAB — teacher-review integration while canonical export stays PASS-only;
3. Score Editor — APP-11G bounded feature work while release/cutover stay closed;
4. Score Following — SF-12 research while research authority remains bounded.

This order is explicit and versioned policy rather than hidden model judgment. If a required truth
gate changes, planning fails closed until the policy is deliberately revised.

Every candidate carries a hash of its complete evidence snapshot. The plan carries a complete
evidence-set hash and deterministic `plan_id`. `execution_authorized` is always false.

`PortfolioPlanningService` registers only one new read-only model tool:

- `music.portfolio.plan`

It performs `collect -> plan -> verify` and returns the source snapshots with the result.

## A14 — Independent verifier

`CrossProjectVerifier` independently recomputes the complete deterministic plan from the supplied
evidence. It does not accept planner reasoning as evidence.

Verification fails when:

- any required project/source is missing;
- evidence schema or a required domain truth gate changes unexpectedly;
- source provenance changes after planning;
- order, action, rationale, constraints or hashes are altered;
- policy versions differ;
- a plan claims it authorizes execution.

This means an LLM can propose prose around a decision, but it cannot silently change the accepted
portfolio plan without failing deterministic recomputation.

## A15 — Verified experience store

`experience.py` adds an append-only learning evidence layer. `ExperienceStore` reuses the existing
sanitized SHA-256 hash-chained journal primitive under a dedicated store identity.

A host may persist an `ExperienceObservation` only when a typed `PlanVerificationReport` proves:

- `status=PASS`;
- observation `plan_id` exactly matches the verified plan;
- `recomputed_plan_id` exactly matches that same plan.

Stored facts are intentionally narrow: project, action, playbook key, outcome and explicit evidence
references. No hidden provider reasoning/chain-of-thought field exists.

The model has no experience-recording tool. Experience writes remain trusted-host operations.

## A15 — Experience advisor

`ExperienceAdvisor` aggregates verified historical outcomes by project + playbook:

- `prefer`: >=3 evaluated attempts and >=80% success;
- `review`: >=3 evaluated attempts and <=50% success;
- `observe`: insufficient/mixed evidence.

Abstentions remain visible but are excluded from success-rate denominator. Every recommendation
sets `auto_apply=false`.

`ExperienceReadToolset` exposes only:

- `learning.experience.summary`

The advisor cannot update prompts, policy, privileges, tool registration, repository code or model
weights. It produces evidence for a later host/human decision.

## A16 continuation

1. Add an execution-outcome contract that binds one completed action to its exact plan candidate,
   branch/commit, CI/validator evidence and final verifier state.
2. Add resumable orchestration state linking plan, execution, journal, budget, approval and
   experience record without persisting provider hidden reasoning.
3. Allow explicit user/business goal profiles to select among versioned planning policies rather
   than silently changing the default order.
4. Add offline evaluation for experience-derived playbook recommendations before any recommendation
   can influence a future planner policy.
5. Define a curated dataset export boundary for possible future fine-tuning; training and model
   promotion remain separate, explicitly evaluated and human-gated stages.

## Architectural invariants

1. Model choice is replaceable.
2. Models cannot grant themselves privileges or approvals.
3. Unknown/unregistered tools never execute.
4. Protected/destructive/external actions cannot silently escalate.
5. Credentials resolve only at trusted adapter boundaries after policy permits execution.
6. File operations cannot escape configured repository/workspace boundaries.
7. Host process execution is not a raw model capability.
8. Executable repository code runs only through an ST-approved sandbox backend.
9. Model-facing output/run traffic is bounded and redacted.
10. Persistent run evidence is sanitized and hash chained.
11. Provider schemas are not host authorization.
12. GitHub model mutation remains limited to reversible feature-branch operations.
13. Run budgets fail closed before overflowing the next action.
14. Approval artifacts are host-generated, exact-match and one-shot.
15. OpenHands raw terminal/editor tools are absent from the bridged agent configuration.
16. External frameworks cannot bypass ST policy, budget or isolation.
17. Music evidence is source-provenanced and cannot silently overstate readiness/authority.
18. Score Restore evaluation success never implies production or Stage 12 authorization.
19. REVIEW_REQUIRED never implies canonical TAB export.
20. Score Editor feature completion never implies release or SesliTab cutover authorization.
21. Score-following research evidence never implies production or pedagogical authority.
22. Portfolio planning is deterministic, versioned and never execution authority.
23. Portfolio verification independently recomputes the accepted plan.
24. Evidence drift invalidates an old plan instead of being silently ignored.
25. Only exact verified outcomes may enter experience history.
26. Models cannot write or rewrite experience history through registered tools.
27. Experience recommendations never auto-apply to policy, code, prompts, privileges or weights.
28. Hidden provider reasoning is not persisted as learning data.
29. Future fine-tuning requires curated data, independent evaluation and explicit promotion gates.
30. Tests define safety behavior before capability is widened.
